# Поток — защищённый учёт личных финансов

Версия 2 использует Vercel для сайта и серверных функций, Supabase для Auth и PostgreSQL. Логин — email. Вход: email и пароль, затем обязательный шестизначный TOTP-код из приложения-аутентификатора. Регистрация требует подтверждения почты.

Google-вход отключён в интерфейсе и серверных маршрутах. Настройки Google-провайдера в вашем Supabase не меняются. Старая реализация остаётся в истории Git.

## Сначала откройте интерфейс

`index.html` можно открыть как файл: так работает только явно обозначенный деморежим. Реальные аккаунты и серверные функции через `file://` недоступны.

Для разработки:

```bash
npm ci
npm run build
npm start
```

Откройте `http://localhost:3000`. Без настроек авторизации страница не выдаёт демоданные за реальные и не разрешает регистрацию. Для отдельного демонстрационного просмотра используйте `http://localhost:3000/?demo=1`.

## Как защищены аккаунты

Браузер обращается только к серверным маршрутам `/api`. Сервер выполняет вход через Supabase, проверяет пользователя, подтверждение почты, существование сессии и второй фактор. Затем делает запросы к базе от имени этого пользователя, сохраняя защиту RLS. Привилегированные `service_role` и `sb_secret_` ключи приложению не нужны.

Реальные пароли и токены не сохраняются в localStorage. Пароли передаются через HTTPS в Supabase Auth; приложение не создаёт собственную таблицу паролей. Сессионные токены находятся в cookie с HttpOnly, Secure и SameSite Strict. Содержимое cookie зашифровано и защищено от изменений AES-256-GCM; в production используется префикс `__Host-`. Браузерный JavaScript не получает access_token или refresh_token в ответах API.

Каждый изменяющий запрос требует точного Origin сайта, JSON и CSRF-токена, связанного с cookie. API-ответы и страницы не кэшируются. CSP ограничивает источники скриптов; загрузка страницы во внешний iframe запрещена. Пользовательские названия операций выводятся через textContent.

Ограничения попыток находятся в PostgreSQL и не сбрасываются при перезапуске функции Vercel. Счётчики используют HMAC-хэши IP/адресов, а не открытые email и IP. При недоступном лимитере вход блокируется. Есть отдельные бюджеты входа, регистрации, восстановления, второго фактора и доступа к данным.

Данные закрыты без AAL2 и активной сессии не только в интерфейсе и API, но и ограничительной политикой PostgreSQL. Прямой запрос к Supabase не обходит эту политику. Проверяется владелец записи. Идентификатор владельца сервер берёт из подтверждённой сессии; клиент не может назначить другой user_id.

Восстановление пароля требует письма и второго фактора, если он уже подключён. Восстановительная сессия не открывает финансовые данные. После изменения пароля пользователь входит заново. Обычный выход завершает сессии на всех устройствах. После отзыва сессии проверка auth.sessions блокирует финансовые запросы даже до истечения JWT.

## Обязательная настройка Supabase

### 1 Создание таблиц и правил

В SQL Editor выполните сначала `database/schema.sql`, затем `database/002_secure_auth.sql` целиком. Если таблица уже создана предыдущей версией, достаточно второй миграции. Миграция не удаляет существующие операции.

После миграции старые сессии без второго фактора не смогут читать финансы. Чтобы получить доступ, пользователи должны войти и подключить TOTP. Не запускайте только первый SQL-файл поверх готовой версии 2 без повторного применения второй миграции.

### 2 Секреты сессии и общего лимитера

На своём компьютере выполните:

```bash
npm run security:keys
```

Команда выводит три значения. Первые два храните только в закрытых переменных окружения Vercel и в локальном `.env`. Третье значение — SHA256-хэш секрета лимитера — внесите в SQL Editor:

```sql
insert into private.auth_security_config(singleton, secret_hash)
values (true, 'ЗДЕСЬ_RATE_LIMIT_SECRET_SHA256_ИЗ_КОМАНДЫ')
on conflict(singleton) do update set secret_hash = excluded.secret_hash;
```

В SQL сохраняется только хэш. Сам `AUTH_RATE_LIMIT_SECRET` передаётся сервером при вызове лимитера и не публикуется в браузере. Не сохраняйте значения секретов в Git и не отправляйте их в чат. Скрипт генерации запускайте локально; не добавляйте его в buildCommand.

### 3 Email и пароли

В Supabase Authentication включите Email/Password и **Confirm email**. В Password Security установите минимум **14 символов** и требование строчной/заглавной латинской буквы, цифры и символа. Эти требования проверяются и сервером приложения, но настройка самого Supabase необходима для защиты его прямого Auth API.

Включите Secure password change / reauthentication и Require current password, если эта настройка доступна. Supabase исключает собственный recovery-flow из требования старого пароля. Включите уведомления об изменении пароля и второго фактора, если они доступны в вашем проекте.

Включите защиту от известных скомпрометированных паролей, если доступна на вашем тарифе: Supabase указывает Pro и выше для этой функции. Приложение не включает платные опции автоматически.

В MFA включите TOTP enrollment и verification. Проверка второго фактора обязательна для доступа к финансам. Нельзя отключать MFA-проверку в Supabase, сохраняя ожидание работы защищённого приложения.

Включите refresh token reuse detection. JWT expiration рекомендуется установить в 15 минут, не ниже 5 минут. При доступности расширенного управления сессиями установите time-boxed session 8 часов и inactivity timeout 30 минут. Независимо от тарифа, cookie приложения имеет максимальный срок 8 часов и 30 минут до истечения; этот короткий срок продлевают успешная проверка MFA, добавление и удаление операции, но не пассивные просмотры или открытая вкладка.

### 4 CAPTCHA

Создайте виджет Cloudflare Turnstile с разрешённым hostname вашего production-домена Vercel. Для локальной разработки добавьте localhost в разрешённые адреса виджета.

Публичный Site Key задайте в Vercel как `TURNSTILE_SITE_KEY`. Secret Key виджета сохраните в настройках Supabase Authentication → Bot and Abuse Protection → CAPTCHA, выбрав Turnstile и включив проверку. **Проверка CAPTCHA в Supabase обязательна**: именно Supabase проверяет одноразовый токен для входа, регистрации и восстановления. Один токен нельзя сначала проверить вручную и затем повторно использовать в Supabase.

В production приложение требует наличие site key и captchaToken и не содержит режима обхода CAPTCHA. Наличие токена в запросе само по себе не доказывает прохождение проверки — подтверждение выполняет настроенный Supabase.

### 5 Адреса и шаблоны писем

В Authentication → URL Configuration задайте Site URL точным адресом production-сайта, например `https://potok-example.vercel.app`. Добавьте тот же адрес с `/` в разрешённые Redirect URLs. Не используйте wildcard для всех чужих preview-доменов.

В Email Templates замените ссылку в письме Confirm signup:

```html
<a href="{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}&amp;type=email">Подтвердить email</a>
```

В Reset password:

```html
<a href="{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}&amp;type=recovery">Восстановить пароль</a>
```

Серверный GET не потребляет одноразовую ссылку. Пользователь открывает страницу и нажимает кнопку подтверждения; обмен выполняется через POST с CSRF-проверкой. Это помогает избежать потребления ссылки почтовыми сканерами. После подтверждения регистрации пользователь всё равно должен войти с паролем; переход по ссылке не открывает чужой аккаунт с доступом к финансам.

Восстановление открывает ограниченную сессию, а адрес аккаунта показан в форме. Приложение удаляет одноразовый token_hash из адресной строки. Не подключайте запись URL, cookies и тел запросов в собственные логи или системы аналитики.

### 6 Почта и лимиты сервиса

Для публичной регистрации настройте собственный SMTP в Supabase: стандартная отправка имеет ограничения и не подходит для полноценного публичного приложения. Используйте подтверждённого отправителя, SPF/DKIM и DMARC для своего почтового домена.

Настройте Authentication → Rate Limits в Supabase. Собственный лимитер защищает сервер Vercel, а встроенные лимиты Supabase защищают прямой Auth API. Они дополняют друг друга. Учтите: запросы Auth от Vercel идут с серверных IP, поэтому слишком маленький глобальный IP-бюджет Supabase может мешать нескольким настоящим пользователям.

## Размещение на Vercel

1. Создайте собственный приватный GitHub-репозиторий из папки проекта и импортируйте его в Vercel. История Git уже включена в архив.
2. Выберите Node.js 22, Framework Preset **Other**. `vercel.json` задаёт Install Command `npm ci`, Build Command `npm run build`, Output Directory `public` и серверную функцию `api/index.js`.
3. В Settings → Environment Variables задайте переменные из таблицы ниже. Для production APP_URL должен точно совпадать с открываемым HTTPS-доменом. Не ориентируйтесь на непроверенный Host из запросов.
4. Выполните Deploy/Redeploy после настройки переменных. Сборка не копирует исходники сервера, `.env`, тесты или SQL в публичный каталог.
5. Настройте Supabase URL Configuration, Turnstile и почтовые шаблоны для полученного production-домена, затем проверьте полный вход.

| Переменная | Значение | Где используется |
| --- | --- | --- |
| APP_URL | Точный HTTPS-origin production-сайта без пути | Проверка Origin и адрес возврата |
| SUPABASE_URL | Project URL Supabase | Только сервер |
| SUPABASE_PUBLISHABLE_KEY | Publishable key или старый anon key | Только сервер |
| SESSION_COOKIE_SECRET | Сгенерированные 32 случайных байта в Base64 | Шифрование и целостность cookie |
| AUTH_RATE_LIMIT_SECRET | Сгенерированный секрет, соответствующий SQL-хэшу | Общий лимитер |
| TURNSTILE_SITE_KEY | Публичный Site Key разрешённого виджета | Форма CAPTCHA |

Google Client Secret, service_role и sb_secret_ здесь не нужны. Они не должны попадать в код или браузер. Публичный Supabase key не заменяет RLS и не считается защитой базы сам по себе.

Для Preview используйте отдельный тестовый Supabase и корректный APP_URL preview-домена. Не подключайте production-данные к чужим веткам и не отключайте проверку Origin ради preview.

Локально скопируйте `.env.example` в `.env`, подставьте значения и используйте APP_URL `http://localhost:3000`. Только loopback HTTP вне Vercel разрешён без Secure-cookie; production требует HTTPS. `.env` исключён из Git.

## Если потерян аутентификатор

Во время первого подключения сохраните TOTP-ключ в защищённом менеджере паролей или используйте аутентификатор с шифрованной резервной копией. Никому не отправляйте QR-код и ключ.

Самостоятельного отключения второго фактора одним письмом или паролем нет. Это преднамеренно: такой обход обесценил бы защиту. Если устройство и резервная копия потеряны, необходима проверенная процедура восстановления владельцем проекта. Не отключайте MFA или RLS глобально, чтобы восстановить одного пользователя.

## Структура и команды

Основные файлы: `js/app.js` — дашборд; `js/auth.js` — формы; `server/handler.js` — API; `server/security.js` — cookie, CSRF, проверки; `database/002_secure_auth.sql` — лимитер и усиление RLS; `vercel.json` — размещение.

БЭМ и модульный SCSS сохранены. Новый `_auth.scss` подключён через @use. Один итоговый CSS находится в dist/css/style.css. Realtime идёт через серверный SSE: токены не отправляются в браузер, а поток уведомляет только об изменениях собственных операций. Соединение регулярно переоткрывается с повторной проверкой сессии.

```bash
npm run build
npm run check
npm test
npm audit --omit=dev
```

17 автоматизированных проверок покрывают серверные ограничения и настоящие SQL-политики в локальном PostgreSQL через PGlite. Браузерный интерфейс также проверен с тестовыми ответами сервера. Подробности — `docs/verification.md`.

Это реализация с несколькими уровнями защиты, а не гарантия невозможности взлома. Облачные настройки, SMTP, CAPTCHA, актуальные зависимости, доступы к Vercel/Supabase и резервные копии тоже влияют на безопасность. Реальный production-вход в вашем проекте ещё не проверен, потому что доступы и ключи не предоставлены.
