# Проверка версии 2

## Пройденные автоматизированные проверки

`npm test`: 17 проверок, все прошли.

Сервер: зашифрованная cookie с изменённым байтом, неверным ключом и истёкшим сроком отвергается; insecure production-конфигурация блокируется; сильный пароль и размер в байтах проверяются на сервере; чужой Origin, cross-site запрос и отсутствие CSRF блокируются; CAPTCHA нельзя пропустить; лимитер блокирует вход при превышении бюджета и при собственной недоступности.

Вход: одинаковый ответ для неверного пароля и отсутствующего пользователя; нейтральная регистрация повторного email; запрет работы при выключенном подтверждении email; отсутствие токенов Supabase в JSON; обязательный второй фактор; восстановительная сессия не читает финансы; пароль меняется только после email-recovery и MFA; выход запрашивает завершение всех сессий.

Данные: сервер проверяет существование сессии и подтверждение почты, использует проверенный user_id и отвергает присланный клиентом user_id. SSE не передаёт содержимое строк или токены и не выдаёт уведомления об удалении чужой записи.

## Проверка настоящих SQL-политик

Оба SQL-файла выполнялись в локальном PostgreSQL через PGlite. Auth-схема и JWT-claims воспроизводились тестовыми фикстурами; это не настоящий Supabase Auth, но запросы и RLS исполнялись самим PostgreSQL.

Проверены чтение только своих строк; запрет создания строки для другого владельца; невозможность удаления чужой записи; отсутствие доступа при AAL1, неподтверждённой почте и удалённой auth.sessions; запрет anon на таблицы данных и приватные счётчики. Общий лимитер отвергает неверный секрет; из восьми параллельно отправленных вызовов с лимитом 3 проходят три. После истечения окна бюджет восстанавливается. Это локальная инстанция PostgreSQL, а не нагрузочный тест распределённого облака.

## Браузер

В Chromium проверены формы входа и регистрации, передача CAPTCHA в API, подключение TOTP, сохранение текущего шага при обновлении сессии/возврате во вкладку, блокировка операций до второго фактора, добавление операции после него и очистка данных при выходе.

Ширины 1440, 768, 390 и 320 px: горизонтального переполнения нет. Вход и мобильная форма визуально проверены. Демо остаётся отдельным режимом и не выдаётся за реальную регистрацию. В реальном режиме приложение не сохраняет данные или сессии в localStorage; ключи старой browser-based интеграции Supabase удаляются при запуске.

Браузерный тест использовал тестовые ответы API и виджета, а не настоящий Turnstile или облачный Supabase.

## Сборка

`npm run build` и `npm run check` прошли. В публичную сборку входят только HTML, браузерные JS, CSS и favicon. Серверные исходники, SQL и секреты в неё не копируются. `npm audit --omit=dev` не сообщил известных уязвимостей установленных production-зависимостей на момент проверки.

## Проверка после размещения

- Миграции и хэш секрета лимитера применены к нужному проекту.
- Подтверждение email, требования к паролю, TOTP и проверка Turnstile включены в Supabase.
- SMTP отправляет письма реальным пользователям; оба шаблона ведут в server confirm endpoint.
- APP_URL совпадает с HTTPS-доменом; CSRF работает на production-домене.
- Registration → email → login → TOTP enrollment → finance проходят полностью.
- В другом браузере вход требует TOTP-код.
- Два настоящих аккаунта не видят данные друг друга.
- После выхода старые сессии не получают финансовые данные; проверка прямого Supabase API также блокируется RLS.
- Recovery не открывает финансы и требует второй фактор для смены пароля.
- Realtime/SSE обновляет собственные операции между вкладками, без уведомлений о чужих строках.
- Установленные cookie имеют Secure, HttpOnly, SameSite Strict и __Host-prefix; API-ответы не кэшируются.
- Секреты не находятся в опубликованных файлах, Git и логах.

Production-размещение и настоящий SMTP/Turnstile/Auth не проверялись: пользовательские облачные проекты и доступы отсутствуют. Автоматизированные проверки не являются независимым аудитом или гарантией отсутствия всех уязвимостей.
